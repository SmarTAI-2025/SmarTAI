## 一、修改的代码文件（10 个）

### 1. 后端 — 多专家评分策略（"任一高置信度即胜出"，2026-08-28）

#### `backend/agents/multi_expert.py`（+68 行）
- **基础设施失败不参与置信度计算**：网络/超时（`transient_llm`）与额度耗尽（`quota_exhausted`）意味着该专家根本没有评分，其置信度（0 或泄漏的假值）一律不进入合并计算（新增 `_casts_confidence_vote`）。
- **置信度新策略**：模型能力参差不齐（如 Qwen 评不了某些主观题、DeepSeek 只评大题），只要有一个自信的专家，合并结果就应是高置信度：
  - 合并置信度不低于最自信专家的置信度（`max` 托底，而不是平均）；
  - `degraded_to_single`（只剩 1 个成功专家）不再强制人工复核，仅当存活样本本身低于低置信度阈值时才标记复核。
- `_weighted_average_fallback` 中置信度由平均值改为 `max`（最自信专家）。

#### `backend/services/grading_adapter.py`（-2 行为主）
- 移除 `_SOFT_REVIEW_METHODS`：`degraded_to_single` 不再被适配器自动加为复核原因；复核标记改由 `run_multi_expert` 在存活样本低置信度时直接打在 Correction 上。

### 2. 后端 — 评分进度与状态修复（2026-08-28）

#### `backend/services/grading_runs.py`
- 租约被抢占/重新领取的轮次开始前 `remove_reporter(run_id)`：防止内存计数器在二次跑批时累加超过 100%（进度条越界、"running" 恒为 0 的回归）。
- 运行进入终态（completed/failed）后移除 reporter，进度页回落到持久化投影。

#### `backend/services/task_facade.py`
- `async_task_state`：把存活 reporter 的**在途单元（active）与更靠前的 completed_units** 合并进持久化进度，修复进度页 "running" 计数恒为 0 的问题（`phase` 仍保持持久化，避免 reporter 提前 `done` 造成假成功）。
- `update_student_answer`：新修订版本的副本会**继承各答案的 review_status**，修复"确认一个答案会把兄弟答案重置为 pending"的问题（"按下葫芦浮起瓢"）。

### 3. 前端 — 复核原因文案

#### `frontend/app/src/components/tasks/resultsModel.ts` / `routes/tasks/results/QuestionAnalysisDetail.tsx`
- 新增 `degraded_to_single` 复核原因的中英文标签："仅单专家成功（低置信度）" / "Only one expert succeeded (low confidence)"。
