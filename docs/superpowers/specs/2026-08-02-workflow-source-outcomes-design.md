# Workflow Source and Per-File Outcome Design

**Date:** 2026-08-02

**Scope:** `DB-W1-1` only

**Baseline:** `c45146f` (`origin/main` when the work began)

**Migration baseline:** `0004_structured_review_reasons`

## Goal

Persist every uploaded workflow source and its per-file terminal outcome without changing existing public APIs, service interfaces, Agent behavior, or the operation lifecycle. A batch must retain failed and conflicting inputs instead of exposing only its successful subset.

This design implements only `DB-W1-1` from `数据库持久化与任务恢复工作安排.md`. `DB-W1-2` operation checkpoint/CAS work remains blocked until this schema and repository contract has been reviewed and merged.

## Frozen Domain Contract

The source outcome vocabulary comes from section 9.2 of `CURRENT_FRONTEND_BACKEND_P0_HANDOFF_AI.md` and is not interpreted or extended by the database layer:

- `parsed`
- `parse_failed`
- `identity_conflict`
- `no_matching_answer`

No `pending` outcome is introduced. A persisted source without an outcome row represents work whose terminal per-file outcome has not yet been recorded. The database layer stores stable error IDs verbatim and does not choose identity, question-matching, override, retry, or grading policy.

## Boundaries

### In scope

- New `0005` Alembic migration.
- ORM records for workflow sources and source outcomes.
- A focused source/outcome repository.
- Owner isolation, idempotency, lineage, aggregation, constraint, migration, SQLite, and PostgreSQL tests.
- Reuse of existing stored-file and workflow-operation records.

### Out of scope

- `backend/services/task_facade.py`, `backend/main.py`, public API DTOs, routes, frontend code, and Agent/OCR behavior.
- `DB-W1-2` checkpoint revision, checkpoint CAS, payload bounds, and terminal operation summaries.
- Upload orchestration and the future rule that an operation may be queued only after every object and metadata record has been saved. The repository supplies the persistence primitive; the integration owner performs that later service/API wiring.
- Identity resolution, question matching, preflight policy, user-facing messages, and retry decisions.
- Changes to migrations `0001` through `0003`.

## Existing Truths Reused

`stored_files` remains the sole source of truth for original filename, storage backend, object key, content type, size, SHA-256 digest, and object linkage. File bytes stay in the configured storage backend.

`workflow_operations` remains the sole source of truth for operation identity, owner, assignment, input hash, and current attempt. The new tables do not copy confirmed questions, submissions, OCR text, model responses, or another operation state machine into JSON.

## Schema

### `workflow_source_items`

Each row identifies one ordered input item for one operation attempt.

| Column | Type | Contract |
|---|---|---|
| `id` | `String(64)` | Stable primary key generated by the repository. |
| `owner_id` | `String(64)` | Required FK to `users.id`; included in every repository predicate. |
| `assignment_id` | `String(64)` | Required FK to `assignments.id`. |
| `operation_id` | `String(64)` | Required FK to `workflow_operations.id`. |
| `attempt` | `Integer` | Positive operation attempt observed when the source is registered. |
| `order_index` | `Integer` | Zero-based, non-negative order within the operation attempt. |
| `stored_file_id` | `String(64)` | Required FK to `stored_files.id`; file metadata is read from this row. |
| `retry_of_source_id` | `String(64)`, nullable | Self-FK to the source being retried. |
| `created_at` | `Float` | Repository creation timestamp. |

Constraints and indexes:

- Unique `(operation_id, attempt, order_index)` so one input position cannot silently change files.
- Unique `(operation_id, attempt, stored_file_id)` so the same stored file cannot be counted twice in one attempt.
- Check `attempt > 0`.
- Check `order_index >= 0`.
- Index `(assignment_id, operation_id, attempt, order_index)` for ordered batch reads.
- Index `owner_id`, `stored_file_id`, and `retry_of_source_id` for isolation and lineage queries.

The repository validates that the referenced assignment, operation, stored file, and optional retry parent all belong to the same owner. The operation must belong to the assignment and its current attempt must equal the requested attempt. On PostgreSQL, source registration locks that owner- and assignment-scoped operation row with `FOR UPDATE` before validating the attempt, so retry and registration cannot cross the attempt boundary. A retry parent must belong to the same operation and a lower attempt; it cannot be the source itself.

### `workflow_source_outcomes`

Each source has at most one immutable terminal outcome.

| Column | Type | Contract |
|---|---|---|
| `source_id` | `String(64)` | Primary key and FK to `workflow_source_items.id`. |
| `status` | `String(32)` | One of the four frozen status IDs. |
| `student_candidate` | `String(255)`, nullable | Opaque candidate identifier supplied by the domain layer; `null` means no candidate was supplied. |
| `matched_answer_count` | `Integer` | Required non-negative count supplied by the domain layer; `0` means no answers matched and is never treated as missing. |
| `unknown_question_ids` | `JSON` | Required bounded list of stable question IDs; `[]` means no unknown IDs and is never treated as missing. |
| `stable_error_code` | `String(128)`, nullable | Stable domain error/reason ID stored verbatim. |
| `retryable` | `Boolean` | Domain-provided retry hint; the repository does not make the retry decision. |
| `artifact_file_id` | `String(64)`, nullable | FK to `stored_files.id` for a bounded artifact reference. |
| `created_at` | `Float` | First successful terminal write timestamp. |

Constraints and indexes:

- Check `status IN ('parsed', 'parse_failed', 'identity_conflict', 'no_matching_answer')`.
- Check `matched_answer_count >= 0`.
- Index `status` and `artifact_file_id`.

The repository rejects non-list `unknown_question_ids`, more than 100 entries, non-string entries, entries longer than 64 characters, and the compact JSON serialization when it exceeds 8192 UTF-8 bytes. This JSON stores identifiers only; it cannot contain original bytes, OCR text, answer bodies, prompts, API keys, or raw model responses.

## Repository Contract

A new focused module, `backend/db/source_outcome_repository.py`, owns these records so `workflow_repository.py` does not grow a second responsibility. It returns detached immutable DTOs composed with stored-file metadata where useful. Existing `save_file()` and `create_operation()` signatures remain unchanged.

### Register source

The registration call accepts owner, assignment, operation, expected attempt, order, stored-file ID, and optional retry parent. In one transaction it verifies all owner and relationship predicates before inserting.

- An identical repeated request returns the existing source.
- Reusing the same attempt/order for a different file or lineage raises the existing `VersionConflict` with the standard `version_conflict` code.
- A stale operation attempt raises `VersionConflict` with the existing `stale_operation_attempt` code already used by workflow operations.
- A missing or wrong-owner assignment, operation, file, or retry source has the same `NotFound` behavior. No error reveals whether another owner has such a record.

### Record outcome

The outcome call verifies the owner-scoped source and optional artifact file, validates the frozen status and bounded identifier list, then inserts the immutable terminal row.

- An identical repeated write returns the existing outcome.
- A different second write raises the existing `VersionConflict`; the repository does not overwrite evidence.
- Concurrent identical inserts produce one new row: one caller receives `created=True` and the other receives the persisted outcome with `created=False`.
- Concurrent differing inserts produce one success and one `VersionConflict`. A uniqueness race is recovered through an owner-scoped re-read and never leaks a raw SQLAlchemy `IntegrityError`.
- Wrong-owner and absent sources are indistinguishable.

### Read and summarize

Owner-scoped getters and ordered list operations include the owner predicate in SQL. Batch summaries are derived from persisted sources and outcomes:

- `parsed` contributes to `success_count`.
- `parse_failed` and `no_matching_answer` contribute to `failed_count`.
- `identity_conflict` contributes to `conflict_count`.
- A source without an outcome contributes to `pending_count`.
- `uploaded_count` is the number of registered source rows.

For a complete batch, `pending_count == 0` and therefore:

```text
uploaded_count = success_count + failed_count + conflict_count
```

An incomplete batch is reported explicitly with its `pending_count`; it is never described as fully successful. The repository does not create a new business status for this condition.

## Failure and Storage Semantics

Object storage and relational metadata cannot share a distributed transaction. The existing `save_file()` behavior remains responsible for deleting a newly saved object if its metadata insert fails. Source registration happens only after that function succeeds. This PR does not wire operation queueing, so it cannot claim end-to-end queue ordering until the integration PR uses the new repository.

Deleting an assignment or operation cascades its source and outcome metadata. Deleting a source cascades its outcome. Stored-file deletion is restricted by foreign keys while a source or artifact references it, preserving audit evidence. The integration layer must retire or replace those references before deleting the object.

## Migration

Migration `0005_workflow_source_outcomes.py` creates `workflow_source_items` first and `workflow_source_outcomes` second. It adds no columns to legacy tables and performs no data backfill because existing uploads cannot be assigned truthful per-file outcomes retrospectively.

Downgrade drops outcomes before sources. It does not mutate `stored_files`, `workflow_operations`, assignments, revisions, results, or any migration from `0001` through `0003`.

SQLite must pass `0004 -> 0005 -> 0004 -> 0005` and the full `head -> base -> head` round trip. PostgreSQL must produce valid DDL and pass the repository isolation/persistence test when `SMARTAI_TEST_POSTGRES_URL` is configured.

## Test Design

Implementation follows red-green-refactor. Tests are added before production code and observed failing for the missing tables/repository behavior.

Repository tests cover:

1. A stored file and matching operation are required before source registration.
2. Twenty sources remain queryable as `18 parsed + 1 parse_failed + 1 identity_conflict`.
3. `no_matching_answer` contributes to failures and is not collapsed into another stored status.
4. Identical source and outcome replays are idempotent; conflicting replacements are rejected.
5. A retry source points to its predecessor and an optional artifact reference remains traceable.
6. Another owner cannot read, list, summarize, or mutate the source/outcome and cannot infer its existence from different errors.
7. Stale operation attempts, negative attempt/order/count values, invalid status values, and oversized/invalid question-ID lists are rejected.
8. File DTOs retain original name, SHA-256, MIME, size, and object key through repository reads.

Migration tests cover:

1. Both new tables, expected columns, foreign keys, checks, unique constraints, and indexes exist at `0005`.
2. Rows present at `0003` remain unchanged through upgrade and downgrade.
3. SQLite upgrade/downgrade/upgrade succeeds.
4. PostgreSQL offline DDL uses portable boolean/default/check syntax and the configured PostgreSQL integration test exercises actual persistence.

Regression verification includes the existing migration, storage persistence, workflow operation, and full backend suites.

## Review and Sequencing Gate

This design and its implementation form the first Week 1 database PR. Model, migration, repository, and contract tests are one indivisible change. No API/Facade/Agent integration is included.

After implementation, the schema and repository must be reviewed and merged before any `DB-W1-2` checkpoint/CAS fields or behavior are developed. `DB-W1-2` must use the merged names and constraints rather than guessing from a parallel branch.
