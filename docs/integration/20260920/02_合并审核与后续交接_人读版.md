## 为什么以前每次都换 base

旧栈类似：`main ← 邮件 ← 结构后端 ← 结构前端 ← 生成 ← 恢复 ← 存储`。结构前端最初以结构后端为 base，GitHub 才能只展示「前端这一层」，而不是连邮件、后端都算进它的 diff。当上一层进入 main 后，把下一层目标改为 main，是让下一次真正合入主干并显示正确范围。

也可以一开始把所有 PR 都设为 main，但在前置尚未合入时，子 PR 的 diff 会包含全部前置，审核和避免重复合并更麻烦。本轮选择一个 main-based 整合 PR，是另一种明确的方案，代价是单 PR 较大；补丁、分层提交与人／AI两版说明用于降低审核负担。

对 GPT 本地测试来说，仅更改 GitHub 的 base 不会改本地文件字节。但 base 会影响比较范围、目标合并树、冲突及 CI；所以不能说「对本地检查完全没影响」。真正应测试的是将要合入 main 的最终组合，不是某个旧父分支上独自通过的代码。
