# OmniDocBench 手写作业人工评分样例

这三个样例用于手动验证：

`题目上传 → 手写图片 OCR → 作答映射 → 人工校对 → 后台评分 → 结果解释`

每个 case 都要创建独立任务，不要把三个 case 当成同一份作业上传。

## 前置条件

- 使用教师账号登录前端；
- 后端运行在 8000 端口；
- 前端运行在 5173 端口；
- 至少配置了一个支持视觉输入的模型；
- 本地已经下载 OmniDocBench。

当前工作区已有前后端进程。通常通过工作区转发的 5173 端口进入；在本机开发环境可打开：

`http://127.0.0.1:5173`

## 推荐操作

### 1. 创建任务

1. 打开教师工作台；
2. 点击“新建任务”；
3. 任务名称填写，例如 `OCR 手测 Case 01`；
4. 创建并进入配置。

### 2. 上传题目

进入“上传题目”，选择当前 case 的 `case_XX_questions.md`。

等待状态变成“题目已就绪”后，检查：

- 题目数量是否正确；
- 题号是否正确；
- 公式是否完整；
- 评分标准是否保留。

如题目解析有误，可以直接在页面修改并保存。题目使用 Markdown，是为了先固定评分基准，把问题集中在学生手写 OCR 上。

### 3. 上传手写作答

点击“继续上传作答”，选择当前 case 对应的 `images/` 图片。

等待状态变成“作答已就绪”后，先不要修改，记录：

- 是否识别出一个学生；
- 学号是否从文件名识别为 `S001`、`S002` 或 `S003`；
- 每道题是否映射到正确题号；
- 手写数字、正负号、分数、上下标是否正确；
- 是否出现 `[unclear]`；
- 是否漏掉推导步骤。

学生姓名不是本轮关键指标；文件名保证了至少有稳定的学生 ID。

### 4. 做两条人工验证轨

**Raw 端到端轨**

保持 OCR 识别结果不变，直接点击“开始批改”。它反映用户今天实际上传图片后的总效果。

**Corrected 评分隔离轨**

新建一个相同任务，重新上传同一组文件；在“作答已就绪”页面手工修正 OCR 文本后再批改。它用于判断：

- Raw 差、Corrected 好：主要是 OCR 问题；
- Raw 和 Corrected 都差：主要是评分、题目映射或评分标准问题；
- Raw 和 Corrected 都好：完整链路基本通过。

不要在同一个任务先批改再修改，因为旧评分不会自动重新执行。

### 5. 查看结果

进入结果页，至少检查：

- 总分和逐题分数；
- 是否指出真正的数学/知识错误；
- 是否把 OCR 错字误判成学生错误；
- 评语是否引用了学生实际写出的步骤；
- 评分总分是否与题目评分标准一致。

当前前端固定向后台发送英文评分语言参数，因此中文样例的评语可能是英文；这与 OCR 是否成功是两个独立问题。

## 各样例的合理预期

### Case 01

- 第 1 题推导得到负指数形式，但题目要求正指数，通常应扣掉最终形式分；
- 第 2 题最后一步把 `4-5b` 写成了 `4+5b`，应识别为符号错误；
- 合理结果约为 4/6，允许评分模型在相邻分值间有小幅差异；
- 如果系统给满分或零分，应重点检查 OCR 转写和评分解释。

### Case 02

- 图片中四道题的关键答案都存在；
- 如果题号映射和公式 OCR 正确，应接近满分；
- 重点关注 `Z^+`、`Z^-`、分式、负号以及 `m=0,-2`。

### Case 03

- 图片覆盖所有题目的主要知识点；
- 正确 OCR 后应获得较高分；
- 重点关注密集中文手写、项目符号、数字和“稀疏/密集”“山谷/山脊”等相似词。

## 限制

- Case 01 是最接近学生答卷的样例；
- Case 02、03 更像学习笔记，只用于测试手写 OCR 和要点评分；
- 这三个样例不能替代真实学生手写作业集；
- 模型评分存在非确定性，优先检查错误定位和理由，不要求每次分数完全相同。
